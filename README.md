# Questa

Прототип мобильного приложения для организации микро-ивентов.
Разрабатывается по документам проекта: «Техническое задание на платформу Questa»
и «Частное техническое задание на MVP» (магистратура ФОМ-150510, УрФУ).

## Что это

Приложение открывается по ссылке в браузере телефона и ведёт себя как нативное:
полноэкранный режим, иконка на домашнем экране, работа с камерой и геолокацией.
Устанавливать ничего не нужно — это снимает риск на защите прототипа.

## Стек

| Слой | Решение | Почему |
| --- | --- | --- |
| Клиент | React + TypeScript + Vite, PWA | Быстрая сборка, запуск с телефона по ссылке |
| Оформление | Tailwind CSS | Палитра и типографика из ЧТЗ 10.2 вынесены в токены |
| Данные | PostgreSQL (Supabase) | Реляционная СУБД из ТЗ 4.1.1 |
| Авторизация | Supabase Auth (JWT) | Схема access + refresh из ТЗ 4.1.3 |
| Чат | Supabase Realtime | Доставка сообщений в реальном времени, ЧТЗ 5.8 |
| Медиа | Supabase Storage (S3-совместимое) | Аватары, обложки, фото-задания |
| Квесты | LLM-генерация по контексту ивента | ТЗ 4.2.6 |

Отличие от production-архитектуры ТЗ (Flutter + Go + Kafka + MinIO) — осознанное:
для прототипа, который нужно показать с телефона, важнее скорость сборки и
отсутствие установки. Слой данных при этом тот же, что в ТЗ, — PostgreSQL.

## Структура репозитория

```
supabase/setup.sql     таблицы, правила доступа и шаблоны квестов
api/generate-quest.ts  ИИ-генерация квеста по контексту (ТЗ 4.2.6)
src/                   код приложения
```

Файлы из `supabase/` выполняются по порядку в SQL-редакторе Supabase:
сперва `setup.sql`, затем `002_photos_and_interests.sql`.
Скрипт проверен на PostgreSQL 16: 17 таблиц, 35 правил доступа, 6 шаблонов
квестов по 3 задания.

## Как получается квест

1. Организатор запускает квест после начала ивента.
2. Контекст ивента — название, описание, категория, адрес, число участников,
   интересы и список мест вокруг — уходит в `api/generate-quest.ts`, оттуда
   в модель.
3. Ответ модели проверяется по схеме: ровно три задания нужных типов, квиз из
   шести вопросов с корректными индексами ответов.
4. Ответы квиза записываются по одному, сразу (миграция 011): квиз
   показывает верный вариант тут же, и без этого его можно было
   переигрывать до полного счёта — выйти и зайти заново. Повторный ответ
   на тот же вопрос база не примет, а экран продолжает с первого
   неотвеченного.
5. Если модель недоступна или ответ не прошёл проверку, задания собираются
   из того же контекста на стороне приложения — квест у ивента будет в любом
   случае.

**Гео-задание — не отметка о присутствии.** Присутствие отмечают на карточке
ивента, и означает оно «я пришёл к началу»: по нему компания видит, что все
собрались. Гео-задание — вылазка: компания отходит от места встречи к другой
точке и проводит там несколько минут. Раньше обе механики указывали на один
адрес, и задание засчитывалось само собой, не успев начаться.

Цель вылазки модель не выдумывает: перед запросом приложение ищет вокруг
места встречи парки, памятники, набережные и заведения (Nominatim, поиск в
рамке примерно полтора километра) и отдаёт список с координатами. Модель
выбирает подходящий по теме номер из списка и говорит, сколько минут там
пробыть. Так точка всегда существует, а приход к ней можно проверить. Ничего
не нашлось — задание остаётся приходом на место встречи, как раньше.

## Жизнь ивента

Создан → набор группы → организатор начинает встречу (тогда же появляется
квест) → завершение → архив.

Пока встреча не началась, организатор может её поправить: перенести,
сменить место, название, описание или число мест. Не бесконечно: не
больше пяти правок, не чаще раза в пять минут, а время и место нельзя
менять, когда до начала меньше часа, — люди уже в пути, и остаётся
только отмена. Об изменениях база сама
пишет в чат и шлёт уведомления участникам, а напоминания переставляет на
новое время. Мест нельзя поставить меньше, чем людей уже записалось.

Завершить можно тремя способами, и два из них не требуют ничьего участия:

* **Организатор нажимает «Завершить»** — обычный путь.
* **Через 6 часов после начала** ивент закрывается сам. Столько идёт долгая
  встреча; всё, что дольше, — уже другой вечер. Ивент, который так и не
  начали, закрывается по тому же сроку от назначенного времени.
* **Напоминания** участникам уходят за сутки, 12, 6 часов, час и полчаса.
  Каждая ступень отправляется один раз; если человек записался за час до
  начала, пропущенные ступени не сыплются пачкой.

И то и другое делает база: функция `run_event_maintenance()` из миграции
008. Планировщика в проекте нет — её вызывает приложение при запуске, и
работа устроена так, что повторный вызов ничего не дублирует. Если проект
переедет на pg_cron, останется добавить расписание — оно записано в самой
миграции комментарием.

Через три часа после конца встречи тем, кто на ней отметился и никого не
оценил, приходит одно напоминание оценить участников. Одно: об оценках
просят единожды, дальше это уже попрошайничество.

**Зачёт встречи.** В статистику («посетил», «провёл») идут только
состоявшиеся ивенты: начатые, длиннее 30 минут, с двумя отметившимися.
Иначе профиль набивался бы за вечер — создал, начал, завершил, повторил.
Очки за выполненные задания при этом остаются: их всё равно нужно было
заработать. Организатора предупреждают об этом до нажатия, а не после.
Отметиться о присутствии можно не раньше чем за час до начала — отметка за
сутки вперёд не говорит ни о чём.

## Экраны

Собраны по макетам Figma: онбординг, регистрация с подтверждением почты,
выбор интересов, главная с рекомендациями, карта с фильтром по категориям,
создание ивента, карточка ивента в трёх режимах, чат, прогресс квеста с
заданиями и квизом, профиль с уровнем и статистикой.

Отбор на карте живёт за одной кнопкой: категория (их шестнадцать, и строкой
они уже не помещаются), день, расстояние и «только со свободными местами».
На самой карте остаётся счётчик — сколько ивентов прошло отбор.

Кнопка «Места рядом» включает слой заведений: кафе, бары и парки вокруг
центра карты, значок по типу места. Карточка места ведёт в Яндекс.Карты —
рейтинг и отзывы есть там, а у OpenStreetMap их нет; показывать выдуманные
звёзды хуже, чем отправить туда, где они настоящие. Оттуда же можно сразу
позвать компанию: «Позвать сюда» открывает создание ивента с уже выбранным
местом.

Магазин из макетов в прототип не вошёл: по ЧТЗ 3.2 он относится к третьему
этапу, за пределы MVP.

## Карта

Карта собирается на JavaScript API Яндекс Карт: векторная схема, русские
подписи, оформление задаётся списком правил в `src/lib/ymaps.ts` — там же
его можно заменить целиком на JSON из Редактора стилей Яндекса. Тем же
ключом работает геокодер: адрес → координаты и обратно.

Запасной вариант — Leaflet с тайлами OpenStreetMap. Он включается сам,
если ключа нет, библиотека не загрузилась или кончилась дневная квота:
в день защиты карта должна показаться при любом раскладе. Экраны об этом
не знают — они работают с общей обёрткой `src/lib/mapview.ts`, у которой
нарочно мало возможностей: метка, круг, линия, перелёт.

Ключ карт лежит в `.env` рядом с ключом Supabase и так же не является
секретом: он уезжает в браузер каждому. Защищает его ограничение по
домену в кабинете разработчика Яндекса — без такого ограничения JS API 3.0
ключ вообще не принимает.

Поиск заведений вокруг («места рядом», цель гео-задания) остался на
Nominatim. Геокодер Яндекса ищет адреса и здания, а не кафе с парками;
для этого у Яндекса отдельный продукт — «Поиск по организациям», — но он
бесплатен только неделю, а постоянная часть приложения не может стоять
на пробном доступе. Рейтингов ни один из этих источников не отдаёт: они
есть только в самих Яндекс.Картах, поэтому карточка места ведёт ссылкой
туда, а своих звёзд приложение не рисует.

## Приглашение по ссылке

Организатор зовёт знакомых ссылкой на встречу. Тот, у кого аккаунта нет,
раньше попадал на экран приветствия: ни названия, ни времени, ни места —
предложение зарегистрироваться неизвестно куда. Теперь по той же ссылке
открывается карточка встречи: обложка, время, адрес, сколько мест занято,
кто зовёт и пара строк о том, что такое Questa. После входа человек
попадает сразу на эту встречу, а не на главную.

Данные для карточки отдаёт функция базы `invite_card` (миграция 013) —
таблицы остаются закрытыми. В карточке ровно то, что отправитель и так
написал в приглашении; участники, чат и задания за входом.

## Два режима работы

Приложение читает адрес и ключ проекта Supabase из `.env`.

**Боевой режим** (ключи заданы) — настоящий вход по e-mail и паролю, данные
в PostgreSQL, чат через Realtime, стрик ежедневного входа, начисление QP и XP
с защитой от повторного зачисления.

**Демонстрационный режим** (ключей нет) — экраны наполняются данными из
`src/data/demo.ts`. Нужен для разработки и как страховка: если база окажется
недоступна, приложение всё равно откроется.

Собрать демонстрационную сборку: `VITE_SUPABASE_URL= VITE_SUPABASE_ANON_KEY= npm run build`.

Разрешены в пользу ЧТЗ, кроме случаев, где это невозможно технически:

| Магазин | Этап 3 | Не реализован | Вне MVP по ЧТЗ 3.2 |

## Запуск

```bash
npm install
npm run dev
```

Адрес проекта и публичный ключ лежат в `.env`. Ключ publishable не секрет:
он и так уезжает в браузер каждому посетителю, а данные защищают правила
доступа в базе. Секретный ключ (`sb_secret_…`) в репозитории не хранится и
приложению не нужен.

## Порядок выполнения SQL

`supabase/setup.sql` → `002_photos_and_interests.sql` →
`003_chat_triggers.sql` → `004_results_and_ratings.sql` →
`005_quest_at_start.sql` → `006_live_notifications.sql` →
`007_achievements.sql` → `008_event_ending.sql` → `009_more_categories.sql` →
`010_event_edits.sql` → `011_quiz_and_edit_limits.sql` →
`012_rate_reminder.sql` → `013_invite_card.sql`. Каждый файл можно
выполнять повторно: они переопределяют функции и не дублируют данные.

Отдельно лежит `supabase/reset.sql` — он в этот порядок не входит и
нужен для другого: стереть все аккаунты и всё, что они создали, оставив
схему, справочники и шаблоны. Пригодится, чтобы начать с чистого листа
перед показом. Отменить его нельзя. Картинки он не трогает: таблицы
хранилища Supabase запросом менять не даёт, их чистят в разделе
Storage → media.

Начиная с 003 системные сообщения и открытие чата делает сама база.
Причина простая: политики доступа разрешают каждому писать только за себя,
поэтому участник не мог ни открыть чат при наборе группы, ни отправить
сообщение без автора. Триггеры выполняются от имени владельца базы.

## Модель для квестов

Функция `generate-quest` пробует поставщиков по очереди и останавливается на
первом, который ответил. Если не ответил никто, приложение собирает задания
само из контекста встречи — квест у ивента будет в любом случае.

| Переменная | Что задаёт |
| --- | --- |
| `AI_BASE_URL`, `AI_API_KEY`, `AI_MODEL` | Любой сервис с протоколом OpenAI: адрес, ключ, название модели |
| `ANTHROPIC_API_KEY`, `CLAUDE_MODEL` | Claude напрямую; ключ должен начинаться с `sk-ant-api` |
| `GEMINI_API_KEY`, `GEMINI_MODEL` | Gemini |

Заданные переменные и определяют порядок: сначала сторонний сервис, затем
Claude, затем Gemini. Незаданный поставщик просто пропускается.

## Скорость первого открытия

Приложение собиралось одним файлом на мегабайт: человек открывал список
ивентов, а телефон качал заодно карту с Leaflet, оформление яндексовской
схемы, экран квеста и страницу самопроверки. Теперь тяжёлые и не всегда
нужные экраны загружаются отдельно, по мере перехода: карта, квест, чат,
создание и правка встречи, архив, чужой профиль, самопроверка.

Первый файл стал 318 КБ вместо 1088 КБ (94 КБ в сжатом виде); карта со
своей библиотекой — 367 КБ — уходит с критического пути и приезжает
только при переходе на вкладку «Карта».

## Состояние работ

Сделано:

- экраны по макетам Figma, публикация на GitHub Pages при каждом изменении;
- база PostgreSQL: таблицы, правила доступа, шаблоны квестов;
- вход по e-mail и паролю, профиль, стрик ежедневного входа;
- ивенты, слоты, автоматическое открытие чата при наборе группы;
- чат в реальном времени, чек-ин, выполнение заданий, начисление QP и XP.

- ИИ-генерация квестов через функцию Supabase, с проверкой ответа модели
  и откатом на шаблон;
- гео-задание: карта, расстояние до цели, таймер присутствия внутри радиуса;
- центр уведомлений и настройки: профиль, пароль, уведомления, удаление;
- анимации: переходы между экранами, появление сообщений, счёт очков.

- отмена ивента организатором и недельная квота на создание;
- процедурные аватары и никнеймы от модели.

- фото-задание: камера, уменьшение снимка, проверка моделью;
- отмена ивента, подтверждения действий, метки с обложками на карте.

- начало ивента организатором, открытие чата триггером базы, полное
  удаление аккаунта серверной функцией;
- места по городам, своя точка и поиск по карте, фото и смайлики в чате;
- итоги ивента и взаимные оценки участников;
- жалобы на ивент, организатора, сообщение и его автора;
- работа без сети: приложение открывается из кэша, полоса о потере
  соединения, повтор неудавшегося запроса при возвращении связи;

- профиль другого участника, архив ивентов отдельным экраном, ачивки;
- ежедневная награда за вход подряд с таймером и обрывом серии;
- идеи для встречи меняются в течение дня и предлагают место рядом.

Дальше: отладка по замечаниям с защиты.

Известные ограничения прототипа:

- подтверждение почты выключено — бесплатная квота Supabase 2–3 письма в час;
- фоновое отслеживание геолокации в браузере невозможно, таймер присутствия
  идёт только при открытом приложении;
- push-уведомления на iPhone требуют установки на домашний экран и iOS 16.4+;
- без сети открывается оболочка приложения и последние загруженные данные:
  новые ивенты, сообщения и квесты всё равно требуют соединения.
